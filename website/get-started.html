Get started

Check your first decision

We will start the service, describe a small contract application in the admin console and ask whether a user may approve a contract. Then we connect a Python program and let an agent work for that user with a narrower set of permissions. The guide assumes Docker and, for the later sections, Python 3.11 or newer.

On this page

  2. Sign in to the admin console
  3. Describe who may do what

1. Start the service

Clone the repository first. Both ways of running the service below use it.

git clone https://github.com/rudi77/authz.git
cd authz

With PostgreSQL and Redis

The included Compose file starts PostgreSQL, Redis and the service, applies the database migrations and configures the admin key dev-key:

docker compose up --build

Wait for the line authz: admin UI on http://localhost:8080/admin/. The first build downloads base images and Python packages and can take a few minutes. Compose publishes PostgreSQL on port 5432 and Redis on port 6379; if other services already use these ports, remove the corresponding ports entries from docker-compose.yml. The service itself does not need them.

As a single container

Without Compose, the service stores its data in SQLite inside a Docker volume. This command is the same in Bash and PowerShell:

docker build -t authz .
docker run --rm -p 8080:8080 -e AUTHZ_API_KEYS=dev-key -v authz-data:/data authz

AUTHZ_API_KEYS sets the key that grants full administrative access. Without it, the service rejects every request, because it is configured to refuse access when no credential is set up.

Check that it answers

# Bash
curl http://localhost:8080/healthz

# PowerShell (curl.exe; "curl" alone is an alias for Invoke-WebRequest)
curl.exe http://localhost:8080/healthz

The response is {"status":"ok","database":"ok"}. A degraded status means the service runs but cannot reach its database.

2. Sign in to the admin console

Open http://localhost:8080/admin/ and enter dev-key as the API key. The key stays in this browser tab unless you choose to remember it. The overview page shows a setup checklist; the next section follows it.

If the page still shows an older interface after an upgrade, reload it once with Ctrl+Shift+R. Later versions of the page are revalidated automatically.

3. Describe who may do what

A permission is a name your application checks, written as resource.action. A role groups permissions, and a membership gives a user roles within one tenant, which is usually one of your customers. Create the following in the console. Each page has a button in its top right corner for this purpose:

PageCreateValues
TenantsNew tenantName ACME Corp, slug acme
ApplicationsNew applicationName Contract AI, slug contract-ai
PermissionsNew permission, three timescontracts.read, contracts.review, contracts.approve
RolesNew rolelawyer, scope Application, all three permissions ticked
UsersAdd userName Alice, provider Any OIDC provider (generic_oidc), issuer https://idp.example.com, subject alice
MembershipsGrant accessAlice with the role lawyer

The tenant and application you create are selected in the switcher at the top, and later pages work within that selection. The provider, issuer and subject identify Alice the way her login token will: in a real application they come from the iss and sub claims of an OIDC token.

For repeatable setups, the authz bootstrap command creates the same structure from a YAML file. See examples/bootstrap.example.yaml.

4. Ask for a decision

Applications do not know authz's internal ids. They know who signed in. The first call therefore turns Alice's identity into ids, and the second asks the actual question.

Bash

curl -s -X POST http://localhost:8080/v1/resolve-context \
  -H "X-API-Key: dev-key" -H "Content-Type: application/json" \
  -d '{"application_id": "contract-ai", "provider": "generic_oidc",
       "issuer": "https://idp.example.com", "subject": "alice"}'

The response contains the ids and Alice's roles and permissions:

{"tenant_id":"30d1d52d-…","application_id":"63347777-…","user_id":"e728c284-…","roles":["lawyer"],"permissions":["contracts.approve","contracts.read","contracts.review"]}

Your ids differ; they are shortened here. Note that application_id takes the application's slug in this call. authz found ACME because it is Alice's only tenant. For a user in several tenants, add "explicit_tenant_id" with the tenant's id, which the Tenants page lets you copy, or configure a tenant mapping. All later calls use the ids from the response. Insert them into the decision request:

curl -s -X POST http://localhost:8080/v1/authorize \
  -H "X-API-Key: dev-key" -H "Content-Type: application/json" \
  -d '{"tenant_id": "<tenant_id>", "application_id": "<application_id>",
       "subject": {"type": "user", "user_id": "<user_id>"},
       "resource": "contracts", "action": "approve"}'
{"allowed":true,"decision":"allow","reason":"permission_granted","required_permission":"contracts.approve","matched_permissions":["contracts.approve"]}

PowerShell

Invoke-RestMethod converts the JSON responses into objects, so the ids can be passed on directly:

$h = @{ "X-API-Key" = "dev-key" }
$who = @{ application_id = "contract-ai"; provider = "generic_oidc";
          issuer = "https://idp.example.com"; subject = "alice" } | ConvertTo-Json
$ctx = Invoke-RestMethod -Method Post -Uri http://localhost:8080/v1/resolve-context `
         -Headers $h -ContentType "application/json" -Body $who

$ask = @{ tenant_id = $ctx.tenant_id; application_id = $ctx.application_id
          subject = @{ type = "user"; user_id = $ctx.user_id }
          resource = "contracts"; action = "approve" } | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri http://localhost:8080/v1/authorize `
  -Headers $h -ContentType "application/json" -Body $ask

See a refusal

Ask again with "action": "delete". The response has "allowed": false and the reason missing_permission, because no role grants contracts.delete. The refusal also appears on the console's Audit log page. The Decision probe page asks the same questions without a terminal.

5. Check from a Python application

The Python SDK wraps these calls. Install it from the repository into the environment of your application:

pip install "git+https://github.com/rudi77/authz.git@main"

The package also contains the service and its dependencies; the client uses only a small part of it. In the console, create a key on the API keys page with the scope runtime. A runtime key can ask for decisions but cannot change roles, which suits an application better than the admin key. Save the following as check.py, replacing the placeholder with that key:

from authz_sdk import AuthzClient, Subject

authz = AuthzClient("http://localhost:8080", api_key="<runtime-key>", cache_ttl_seconds=60)

# In a web application these values come from the verified login token.
ctx = authz.resolve_context(
    application_id="contract-ai",
    provider="generic_oidc",
    issuer="https://idp.example.com",
    subject="alice",
)
alice = Subject(type="user", user_id=ctx.user_id)

for action in ("approve", "delete"):
    result = authz.authorize_decision(
        tenant_id=ctx.tenant_id, application_id=ctx.application_id,
        subject=alice, resource="contracts", action=action,
    )
    print(f"contracts.{action}: {result.decision} ({result.reason})")

print(sorted(authz.get_effective_permissions(
    tenant_id=ctx.tenant_id, application_id=ctx.application_id, subject=alice)))
python check.py
contracts.approve: allow (permission_granted)
contracts.delete: deny (missing_permission)
['contracts.approve', 'contracts.read', 'contracts.review']

In a web framework, the same check usually runs before a request handler. authz.require(...) raises PermissionDeniedError on a refusal, which you can translate into an HTTP 403 response. The effective-permission list is cached for 60 seconds here, so a role change can take that long to appear in it; authorize_decision always asks the service.

6. Let an agent work for the user

Suppose an AI agent should read contracts for Alice and leave review comments, but never approve anything. Register it on the console's Agents page and give it a role of its own:

  1. On Roles, create analyzer with scope Agent and the permissions contracts.read and contracts.review.
  2. On Agents, register contract-analyzer. The analyzer role is preselected. Copy the agent's id.

The agent may now do what both it and Alice may do: contracts.read and contracts.review. Alice's approval right does not carry over, because the agent's role lacks it. For one particular run you can narrow this further with a delegation grant, a signed token limited to selected permissions and a time span. Grants need a signing key, which the single-container setup creates automatically; with Compose and PostgreSQL, create it once:

docker compose exec authz authz oauth signing-key generate

Append the following to check.py, replacing <agent-id>:

from authz_sdk import PermissionDeniedError
from authz_sdk.agent_session import start_delegated_agent_session

grant = authz.create_delegation(
    tenant_id=ctx.tenant_id, application_id=ctx.application_id,
    user_id=ctx.user_id, agent_id="<agent-id>",
    permissions={"contracts.read"}, ttl_seconds=900,
    purpose="Summarise NDA #42",
)

# The agent runtime receives only grant.token.
guard = start_delegated_agent_session(authz, grant.token)
print("agent may:", sorted(guard.permissions))
try:
    guard.require("contracts", "review")
except PermissionDeniedError as exc:
    print("refused:", exc.permission)

authz.revoke_delegation(grant.id)
print(authz.introspect_delegation(grant.token))
agent may: ['contracts.read']
refused: contracts.review
{'active': False, 'reason': 'delegation_revoked'}

The guard checks permissions locally against the set it loaded at the start, so guard.require costs no network call. That also means a revocation reaches it only when the guard asks the service again; list actions that need this in critical_actions. The article on delegating access follows this run in detail. The Delegations page in the console lists active grants and can revoke all grants of an agent at once.

7. Prepare a real deployment

The steps above use a development key and default settings. Before other people depend on the service, change at least the following:

  • Replace dev-key with a long random value, for example from python -c "import secrets; print(secrets.token_urlsafe(32))". Give applications runtime keys created in the console.
  • Use PostgreSQL and set AUTHZ_RUN_MIGRATIONS=true, or run alembic upgrade head before each upgrade. With PostgreSQL, the service does not change the schema by itself.
  • Set AUTHZ_OAUTH_SIGNING_KEY_PEM if you use delegation grants or OAuth tokens, so the key is managed outside the database.
  • Configure admin sign-in through your identity provider, or place /admin behind an authenticating proxy.

SECURITY.md contains the complete hardening checklist, and the configuration reference lists every setting.

8. Troubleshoot the first run

SymptomWhat to check
Every request returns 401 missing_or_invalid_api_keySend the key in the X-API-Key header and check that it matches AUTHZ_API_KEYS.
The container exits with exec /usr/local/bin/docker-entrypoint.sh … No such file or directoryYour checkout predates the line-ending fix for Windows. Pull the current version and rebuild.
The admin page shows an error or an older layoutReload with Ctrl+Shift+R, and confirm with git log -1 that the build used the current code.
resolve-context answers 400 unknown applicationThis call expects the application's slug, such as contract-ai, not its id.
resolve-context answers 404 no_active_membershipThe user exists but has no active membership in this tenant. Grant one on the Memberships page.
A decision is denied with tenant_feature_disabledThe tenant's permission mask excludes this permission. See Feature controls.
Issuing a delegation returns 503 signing_key_unavailableCreate a signing key as shown in section 6.

The feature guide explains what to add next. The interactive API reference is available at http://localhost:8080/docs while the service runs.
