Features

What you can do with authz

Every capability below serves one of three questions: who is asking, what they may do, and whether you can later explain the answer. The sections are ordered roughly as an application adopts them. The getting-started guide contains the commands for a first run.

Describe permissions and roles

A permission is the name of something your application checks before acting, for example contracts.approve. The convention is resource.action, with an optional namespace in front: mcp.github.create_issue. authz compares these names exactly and does not interpret the dots, so contracts.* is an ordinary name and not a wildcard.

Permissions belong to an application. A role groups some of them under a name such as lawyer. Users receive roles through memberships, and agents receive roles directly. A role's scope documents whom it is intended for: application roles for people, agent roles for agents, and tenant roles that exist only within one customer. Saving a role's permissions replaces the complete list, so the stored state always matches what you last sent.

PUT /v1/roles/{role_id}/permissions
{"permissions": ["contracts.read", "contracts.review"]}

The authz bootstrap --spec FILE command creates a tenant, an application, its permissions, roles and agents from a YAML file and can be run repeatedly. It suits test environments that are rebuilt often.

Serve several customers

A tenant usually corresponds to one customer organisation. Memberships, agents and audit records belong to a tenant, and every decision names the tenant it concerns. A user can be a member of several tenants with different roles in each.

Suspending a tenant or an application makes every decision within it return tenant_not_active or application_not_active. This is useful when a contract ends but its data must be kept.

A permission mask limits what a tenant may use at all, independently of anyone's roles. If ACME has not bought contract approval, leave contracts.approve out of ACME's mask. Requests for it are then denied with tenant_feature_disabled instead of missing_permission, which tells support staff that the cause is the customer's plan and not a missing role. An empty mask means no restriction.

PUT /v1/tenants/{tenant_id}/applications/{application_id}/permission-mask
{"permissions": ["contracts.read", "contracts.review"]}

Feature flags store arbitrary JSON values per tenant, optionally per application, such as {"max_documents": 500}. authz does not evaluate them in decisions; your application reads them through the management API, which requires an admin-scoped credential.

Recognise users from their login

Your identity provider signs users in and issues a token. Its claims describe the user, but in a provider-specific shape: Microsoft Entra uses oid and tid, Cognito uses sub and custom attributes. POST /v1/resolve-context takes the provider, issuer and subject from that token and returns the internal user id, tenant id, roles and permissions.

Provider valueIntended for
azure_entraMicrosoft Entra ID
aws_cognitoAmazon Cognito user pools
gcp_identityGoogle Cloud Identity
generic_oidcAny other OpenID Connect provider, such as Keycloak

An unknown user is created on first sight (AUTHZ_AUTO_PROVISION_USER, enabled by default), but receives no roles until someone grants a membership. The tenant comes from explicit_tenant_id, or from a tenant mapping that links the provider's tenant identifier, such as an Entra tid, to a tenant. Tenants are not created automatically unless AUTHZ_AUTO_PROVISION_TENANT=true, because adding a customer is a business decision.

Invitations cover users who have never signed in. An administrator invites an email address with roles and receives a one-time token. Your application delivers it, and when the user signs in and redeems it through POST /v1/invitations/{token}/accept, authz creates the membership. Users can also be added in advance in the admin console.

Check a permission in your application

Three calls answer the question in different shapes. All three require a credential with the runtime or admin scope.

CallUse it whenResponse
/v1/authorizeA user or agent is about to perform one action.allowed, a reason and the required permission.
/v1/bulk-authorizeYou need many answers for the same subject, such as which of 30 tools to offer.One result per check, computed from a single permission lookup.
/v1/effective-permissionsYou want to show or hide interface elements, or check locally afterwards.The complete permission list at this moment.

A refusal always carries a reason. The most common are missing_permission, no_active_membership, tenant_feature_disabled and, for agents, agent_not_active. Log the reason: it distinguishes a configuration gap from an intentional refusal.

The Python, Go and TypeScript clients can cache effective permissions for a configurable time. A cached list does not see role changes until it expires, so use a short time or call authorize for actions where a revocation must apply immediately. Mutating requests accept an Idempotency-Key header, and an X-Request-Id header is copied into the audit record.

Let agents act for users

An agent is registered within a tenant and application and receives roles like a user. It never acts on its own, though: every agent decision names the user it is working for. The permissions that apply are those the user and the agent hold, further limited by the tenant's mask.

user (lawyer):   read, review, approve
agent (analyzer): read, review, classify
effective:        read, review

This intersection limits what a manipulated prompt can achieve. If text in a contract persuades the agent to approve it, the request fails with missing_permission, because the agent's role lacks approval. If the agent's role contained approval but the user's did not, the result would be the same. A suspended membership or a suspended agent ends the agent's access as well.

The intersection is computed for each decision. The article on delegating access follows a complete agent run.

Narrow a single agent run

Agent roles are fixed per agent. A delegation grant restricts one particular run further: for the next 15 minutes, this agent may only read contracts for Alice. Your application issues it while the user is signed in, and the agent runtime sends it with its checks in the X-Delegation-Token header.

  • Decisions with a grant use user ∩ agent ∩ mask ∩ grant. A grant can never add a permission; requesting one outside the intersection is refused at issuance.
  • The grant is a signed JWT whose claims follow RFC 8693: sub is the user, act.sub the agent, jti the grant id. Other services can verify it with the keys from /v1/delegations/jwks.
  • Revocation is checked on every call. POST /v1/delegations/revoke ends all grants of an agent or user at once.
  • Denials name the cause: not_delegated, delegation_expired, delegation_revoked or delegation_mismatch.

Grants are optional. Without the header, agent decisions behave as described in the previous section. AUTHZ_DELEGATION_REQUIRED=true makes a grant mandatory for every agent decision. Issuing a grant currently requires a runtime credential and trusts its holder to have authenticated the user; the grant does not yet contain proof of the user's own login.

Guard tools and MCP servers

An agent runtime may call dozens of tools in a single run, and asking the service before every call would add latency. The Python library therefore provides guards that check against a permission set loaded once:

from authz_sdk import MCPGuard

guard = MCPGuard(permissions)           # e.g. from get_effective_permissions
guard.allowed_tools("github")           # ["read_repo"] -> offer only these to the model
guard.require("github", "create_issue") # raises PermissionDeniedError

ToolGuard does the same for local tools named resource.action, and MCPGuard for MCP tools named mcp.<server>.<tool>. AgentGuard, created by start_agent_session, adds critical actions: for these it asks the service again, so a revocation takes effect within the run. Offer the model only allowed tools and check again before execution. The first step keeps unusable tools out of the prompt, the second catches a call the model produces anyway.

Add conditions on resource data

Roles answer whether someone may approve contracts in general. Some rules depend on the particular contract, for example agents may only classify contracts below 10,000 EUR. The library contains a policy engine for such conditions. It runs after the role check and can only remove permissions, never add them.

# Excerpt: store is your repository, e.g. a SqlAlchemyStore or InMemoryStore.
from authzkit import AuthorizationEngine
from authzkit.policies.engine import PolicyEngine, PolicyRule

rule = PolicyRule(
    name="agents-small-contracts-only", effect="deny",
    resource="contracts", action="classify",
    condition={"and": [{"eq": ["subject.type", "agent"]},
                       {"gte": ["resource.amount", 10000]}]},
)
engine = AuthorizationEngine(store, policy_engine=PolicyEngine([rule]))

The resource attributes travel in the request's context, for example {"resource": {"amount": 25000}}. With the rule above, an agent asking to classify a 25,000 EUR contract is denied with policy_condition_failed, while the same agent may classify a 500 EUR contract and a user may classify either. A matching deny rule wins; every matching allow rule must hold. Supported operators are eq, ne, lt, lte, gt, gte, in, not_in, and, or and not.

Current limit: the HTTP service starts with an empty rule set and offers no API for rules yet. Conditions are available when you embed the Python library in your own process, as in the example above.

Authenticate callers

Every API request needs a credential; only health checks, metrics, public keys and the console's static files are open. Its scope decides what the caller may do: admin may change configuration, runtime may ask for decisions and manage delegation grants, and tenant:<id> limits a runtime caller to one tenant.

  • Bootstrap keys from AUTHZ_API_KEYS always have the admin scope. Use them to set up the service and for emergencies.
  • Stored API keys are created in the console or through /v1/api-keys. Only a hash is stored. Rotating a key creates a successor with the same scopes; revoke the old key once callers have switched.
  • OAuth access tokens: authz can accept JWTs from your own identity provider (AUTHZ_OAUTH_RESOURCE_ISSUERS) and can issue its own through the client_credentials grant at /oauth/token (AUTHZ_OAUTH_AS_ENABLED=true).
  • Admin sign-in through your identity provider replaces pasted keys in the console with a session cookie (AUTHZ_ADMIN_OIDC_*).

Without any configured credential, the service rejects all requests. AUTHZ_DEV_MODE=true accepts every caller for local experiments until the first stored key is created, and logs a warning at startup.

Manage everything in the admin console

The console at /admin/ is part of the service and needs no separate installation. It covers tenants, applications, permissions, roles, users, memberships, agents, invitations, delegation grants, feature controls, API keys and OAuth clients. The Decision probe asks the engine the same question an application would, and the overview page shows a setup checklist for the selected tenant and application.

The console uses the same REST API as every other client. Changes made in it are therefore equivalent to API calls with the signed-in admin's credential.

Explain and monitor decisions

Every refusal is written to the audit log with tenant, user, agent, permission, reason and, where present, the delegation grant. Allowed decisions are recorded as well when AUTHZ_AUDIT_ALL=true. The console's Audit log page and GET /v1/audit list recent entries, newest first. AUTHZ_AUDIT_RETENTION_DAYS deletes older entries in the background; by default nothing is deleted.

/metrics exposes Prometheus metrics such as authz_decisions_total, authz_decisions_by_reason_total and authz_decision_latency_seconds. /healthz reports database reachability and /readyz readiness for load balancers.

Run several service processes

Decisions themselves keep no state in the process, so several service instances can share one PostgreSQL database. Two optional mechanisms hold state between requests: the rate limit (AUTHZ_RATE_LIMIT_PER_MINUTE, off by default) and idempotent replay of POST requests. With AUTHZ_REDIS_URL set, both use Redis and therefore apply across processes; otherwise each process keeps its own memory.

Schema changes are shipped as Alembic migrations. The container runs them on start when AUTHZ_RUN_MIGRATIONS=true. The project changes the HTTP API additively: new endpoints, optional fields and new reason values are added, and existing requests keep their behaviour. The design principles explain how this is checked.
