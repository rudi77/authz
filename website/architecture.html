Architecture

From a question to a decision

This guide follows one authorization request through the service: who sent it, which permissions apply, what the answer is and where it is recorded. The later sections cover identities, storage and the parts that matter when several service processes run. Each section links to the source file that implements it.

1. Following one request

An agent working for Alice wants to read a contract. Its runtime sends POST /v1/authorize with the tenant, application, a subject {"type": "agent", "user_id": …, "agent_id": …} and the permission contracts.read, split into resource and action. The request passes these stages:

The distinction in the caption matters for integrators. An HTTP error means the caller could not ask the question, for example because its key is wrong. "allowed": false means the question was asked and answered. Your code should treat both as "do not proceed", but only the second is a statement about the subject's rights.

2. Identifying the caller

The caller is the program sending the request, which differs from the subject the question is about. require_caller turns the request's credential into a principal in this order:

  1. An X-API-Key header, or a bearer value that does not look like a JWT, is compared with the bootstrap keys from AUTHZ_API_KEYS and then with the hashed keys stored in the database.
  2. A bearer JWT is checked against the configured token issuers, or against the service's own signing keys if it issued the token.
  3. Without either, a session cookie from admin sign-in is accepted; changing requests must then carry the session's CSRF token.

Each principal has scopes. The decision endpoints accept runtime and admin, and a principal bound to a tenant may only ask about that tenant. Key comparisons use constant-time functions so that response timing does not reveal how much of a key was correct.

3. Computing the permission set

AuthorizationEngine.authorize contains the entire decision logic. It works through these steps and stops at the first refusal:

  1. Check that the tenant and the application are active, otherwise tenant_not_active or application_not_active.
  2. For a user: find an active membership, preferring one for this application over a tenant-wide one, and collect the permissions of its roles. Without a membership the answer is no_active_membership.
  3. For an agent: require an active membership of its user and an active agent, then keep only permissions held by both.
  4. Intersect the result with the tenant's permission mask, if one is configured.
  5. Look for the requested permission. If it is missing because of the mask, answer tenant_feature_disabled, otherwise missing_permission.
  6. Evaluate policy conditions, if the engine was created with rules. A failed condition gives policy_condition_failed.
effective = (user_permissions ∩ agent_permissions) ∩ tenant_mask
allowed   = required_permission in effective and conditions hold

The engine reads through a repository interface. The service uses a SQLAlchemy implementation, while tests and embedded use can pass the in-memory store. Because the engine has no HTTP dependency, the same rules apply whether a Python program embeds it or calls the service.

4. Applying a delegation grant

If the request carries X-Delegation-Token, apply_delegation runs before the engine. DelegationService.verify checks the token's type header, signature, audience, issuer and expiry, then loads the grant's database row by its id. A revoked or expired row rejects the token even if its signature is still valid, and the signed claims must match the stored row.

The grant must also fit the request: the subject has to be an agent, and tenant, application, user and agent have to match the grant. If the request's subject omits the user or agent id, they are taken from the grant. The engine then receives the grant's permission list and intersects it with the result of step 4 above. A permission the agent could otherwise use but the grant excludes is refused with not_delegated.

Grants are signed with the same keys as the OAuth access tokens the service can issue. To keep the two apart, grants use their own type header and audience, carry no scope claim, and the bearer-token check refuses the grant type outright.

5. Answering many checks at once

An agent runtime deciding which tools to offer may ask about 30 permissions for the same subject. bulk_authorize performs steps 1 to 4 of the engine once and then answers every check against the same set. Only policy conditions run per check, because they can depend on per-resource data in the request's context. effective_permissions returns the set from step 4 directly, without conditions.

The client libraries can cache effective permissions for a configured time. Caching moves a revocation's effect to the end of that time. The Python AgentGuard therefore re-asks the service for actions listed as critical.

6. Recording the decision

After the engine answers, the route writes an audit entry with the request, the response, subject ids and the request id. The audit sink stores every refusal and stores allowed decisions only when AUTHZ_AUDIT_ALL=true, because a busy agent can produce thousands of allowed checks per minute. A grant id is added to the stored request when one was used.

The same request also updates Prometheus counters by decision and reason, and a latency histogram. A background worker deletes audit rows older than AUTHZ_AUDIT_RETENTION_DAYS when that setting is positive.

7. Resolving a login into ids

The decision endpoints expect internal ids. Applications obtain them with POST /v1/resolve-context, implemented by TenantContextResolver:

  1. Find the user by provider, issuer and subject, or create one if user provisioning is enabled.
  2. Determine the tenant from explicit_tenant_id or from a tenant mapping for the token's external tenant id.
  3. Find the user's active membership for the application, falling back to a tenant-wide one.
  4. Return the ids, the role names and the resulting permissions.

The identity normalizers convert provider-specific claims into one IdentityPrincipal shape. They are where Entra's oid and tid or Cognito's attributes are interpreted; the rest of the code only sees the normalized form.

8. Storing configuration

Tenants, applications, users, memberships, roles, permissions, agents, grants, keys and audit entries live in one relational database. orm.py defines the tables and SqlAlchemyStore implements the repository on top. PostgreSQL is the production target; SQLite serves tests and the single-container setup.

Schema changes ship as Alembic migrations. With SQLite, the service creates missing tables at startup. With PostgreSQL it leaves the schema alone, so that an accidental deployment cannot change a production database; run alembic upgrade head or set AUTHZ_RUN_MIGRATIONS=true in the container.

9. Sharing state between processes

Decisions read only from the database, so any number of service processes can answer them. Two features keep short-lived state: rate limiting counts requests per caller, and idempotent replay stores the first response for an Idempotency-Key. Each has an in-memory and a Redis implementation behind one interface; AUTHZ_REDIS_URL selects Redis at startup in middleware.py. Without Redis, every process counts and replays on its own.

10. Serving the admin console

The console is a set of static files in authz_service/ui, served under /admin/. It has no build step and no server-side rendering: the JavaScript calls the same REST endpoints as any other client, with the API key from the sign-in screen or with the session cookie from admin sign-in. The files are sent with Cache-Control: no-cache, so browsers check for a new version on every load.
