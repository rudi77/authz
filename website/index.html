Decide what users and their agents may do.

authz answers one question for your applications: may this user, or an agent working for this user, perform this action in this tenant? Your application asks before it acts and enforces the answer. authz keeps the roles, records the decision and explains a refusal.

Signing in stays with your identity provider, and the approval itself stays in your application. authz supplies the decision in between.

Start with one decision

authz runs as an HTTP service. With Docker installed, you can start it with a single container that stores its data in SQLite:

docker build -t authz https://github.com/rudi77/authz.git
docker run --rm -p 8080:8080 -e AUTHZ_API_KEYS=dev-key -v authz-data:/data authz

The admin console at http://localhost:8080/admin/ lets you create a tenant, an application, permissions such as contracts.approve and a role that bundles them. Once a user holds that role, your application can ask for a decision:

POST /v1/authorize
{"tenant_id": "…", "application_id": "…",
 "subject": {"type": "user", "user_id": "…"},
 "resource": "contracts", "action": "approve"}

-> {"allowed": true, "reason": "permission_granted", …}

This is a shortened request; the getting-started guide walks through the complete sequence, including how your application obtains the three ids from a signed-in user. Python applications can use the SDK instead of building requests by hand.

When access control becomes harder

A single role check is easy to write directly into an application. The difficulty grows with customers who need separate settings, products that share users, and AI agents that act on someone's behalf. authz has a dedicated mechanism for each of these situations.

Serve several customers

Each tenant has its own members and roles. A permission mask can switch off features a customer has not bought, and the refusal says so.

Recognise users from their login

resolve-context turns the claims of an Entra, Cognito, Google or other OIDC token into an internal user, tenant and role set.

Let an agent act for a user

An agent receives only what both it and its user may do. A prompt cannot talk it into an action the user could not perform.

Narrow a single agent run

A delegation grant limits one run to selected permissions and an expiry time, and can be revoked while the agent is working.

Guard tools and MCP servers

ToolGuard and MCPGuard check a preloaded permission set before each tool call, without a network round trip per call.

Explain what happened

The audit log records every refusal with its reason, the user and, where relevant, the agent and grant involved.

Choose where to check

Most applications start with one call per protected action. Agent runtimes usually load the whole permission set once per run and check locally afterwards.

SituationCallWhat you get
A user triggers a protected action in your web appPOST /v1/authorizeAllow or deny with a reason such as missing_permission.
Your UI decides which buttons to showPOST /v1/effective-permissionsEvery permission the user currently holds, ready to cache.
An agent decides which of 30 tools it may offer the modelPOST /v1/bulk-authorizeOne decision per tool from a single request.
An agent should handle one task for a limited timePOST /v1/delegationsA signed grant the agent runtime sends with its checks.

authz does not authenticate users and does not run tools. Its answer protects your system only where your code checks it before acting.

Read the implementation

The decision logic lives in one Python class, AuthorizationEngine, which the service wraps in a FastAPI application. The same library can be embedded directly in a Python program. The architecture guide follows a request from authentication to the audit record and links to the source of each step.

The test suite runs against SQLite without external services, so the decision rules can be checked on any machine. Production deployments use PostgreSQL and, for several service processes, Redis.
