Design principles

The reasons behind the design

An authorization service is trusted with decisions that other systems act on without looking again. The principles below explain how authz tries to deserve that trust, which example in the code shows each one, and what it costs. Contributors can use them as review questions.

On this page
  1. Decide; let the application enforce
  2. An agent never exceeds its user
  3. Refuse when the setup is incomplete
  4. Keep the decision in one place
  5. Explain every refusal
  6. Make the frequent check cheap
  7. Change the API additively
  8. Test without external services

Decide; let the application enforce

authz answers whether an action is allowed. It does not sign users in, does not proxy requests and does not run tools. In security terms it is a policy decision point; the application or agent runtime that acts on the answer is the policy enforcement point.

This split lets one permission model serve a Python web application, a Go service and an agent runtime alike, because each of them only needs to ask a question over HTTP. The cost is that protection depends on every protected code path asking. A forgotten check is not caught by authz. The SDK helpers, such as the FastAPI dependency and the tool guards, exist to make the check hard to forget.

An agent never exceeds its user

An agent decision always names the user the agent works for, and the result is the intersection of both permission sets. The rule is applied inside the engine, in the same function that handles users, rather than in an optional helper. An integration therefore cannot accidentally skip it.

The reasoning is that an agent's behaviour depends on text it reads, and that text can be written by someone else. If a contract contains instructions to approve it, the worst outcome should be an action the user could have performed anyway, and only one the agent's role covers. The cost is administration: each agent needs a role of its own, and an agent whose role lacks a permission cannot use it even for a user who has it. Delegation grants extend the same idea to individual runs; they can only remove permissions.

Refuse when the setup is incomplete

When a required piece of configuration is missing, authz refuses instead of guessing a permissive default:

  • Without any configured credential, every request is rejected. Accepting all callers requires the explicit setting AUTHZ_DEV_MODE=true, and even that switches itself off once the first stored key exists.
  • With PostgreSQL, the service does not create or change tables at startup. Migrations run only when someone requests them.
  • A signing key for grants is generated automatically only with SQLite, where it lives in the same file as the data it protects. With PostgreSQL, an operator creates or supplies one.
  • An agent whose user has no active membership is refused, even if the agent itself is active.

The cost is visible in the getting-started guide: a first run needs an API key and, for grants on PostgreSQL, one extra command. A deployment that forgot these steps fails immediately, where a permissive default would have allowed requests nobody intended to allow.

Keep the decision in one place

All decision rules live in AuthorizationEngine. The HTTP routes translate requests and responses, the delegation check narrows the input, and the admin console calls the same API. None of them contains a second version of the rule.

When delegation grants were added, for example, the engine received an optional permission subset and applies it at the point where it already applies the tenant mask. The route only verifies the token. A reviewer can therefore check the complete decision by reading one class, and the embedded library and the service cannot drift apart.

Explain every refusal

A refusal carries a reason code such as missing_permission, tenant_feature_disabled, no_active_membership or delegation_revoked. The codes are distinct on purpose: each one points to a different fix. A missing permission is a role question, a disabled feature is a contract question, a missing membership is an onboarding question.

Refusals are always written to the audit log, so the explanation is available afterwards as well. Allowed decisions are not logged by default because their volume would hide the refusals; AUTHZ_AUDIT_ALL=true records them when an audit requires it.

Make the frequent check cheap

An agent run can involve dozens of tool calls, and a page in a web application can contain many protected buttons. A network request per check would add noticeable latency. authz offers three ways to reduce this: bulk-authorize answers many checks for one subject from a single permission lookup, effective-permissions returns the whole set for local checks, and the clients can cache that set.

Local checks trade freshness for speed. A cached set does not notice a revoked role until the cache expires. The Python AgentGuard therefore lets you name critical actions that are always checked by the service. Choose the cache time according to how quickly a revocation must take effect for your application.

Change the API additively

Applications and agent runtimes depend on the HTTP API, often in environments where they cannot be updated together with authz. Changes therefore add endpoints, optional fields, optional headers or new reason values; they do not rename or remove existing ones or change the meaning of an existing request.

The delegation grants illustrate the approach. They added new endpoints and the optional X-Delegation-Token header. Before the change was merged, the OpenAPI document of the service was compared with the previous version to confirm that no existing path, request body or response schema had changed, and the existing tests were kept unchanged. A request without the header behaves exactly as before. Clients should still treat unknown reason values as refusals, because new reasons can appear.

Test without external services

The Python test suite runs the complete service in-process against temporary SQLite databases, with Redis replaced by an in-memory fake. It needs no network and no running containers, so every contributor can run it before a change. At the time of writing it contains about 230 tests, including end-to-end checks of delegation grants and the admin API.

The cost is that some production behaviour is outside the default run. PostgreSQL-specific locking and Redis's Lua scripts are not covered by the in-memory variants; changes to migrations or shared-state code need an additional check against the real services. OPEN_ITEMS.md tracks these gaps.
